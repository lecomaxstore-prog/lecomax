# Manual SEO synchronization and shared run control

Prepared locally only. No production database changes, deployment, secrets change, or scheduler activation. Previous candidates, SQL and backups remain retained.

The Admin SEO dashboard now offers **Run SEO Sync** to an owner or active administrator with products.view, products.edit and categories.edit. POST `/api/admin/seo/sync` uses the existing session, same-origin and rate-limit protection (three requests per minute per existing process-local IP bucket). Permissions are re-read for each request. Product-only and view-only staff cannot trigger a whole-catalogue reconciliation or read its global run statistics.

The route calls the dedicated Vercel worker; it contains no processing loop or database mutation implementation. It uses server-only `SEO_WORKER_URL` (exact HTTPS production `*.vercel.app/api/sync` URL, no credentials/query/fragment), `SEO_WORKER_CRON_SECRET` (matching the dedicated worker's CRON_SECRET), and `SEO_MANUAL_SYNC_ENABLED=true`. Manual execution also requires VERCEL_ENV=production. Keep the flag absent/false until separately approved. Worker configuration and its activation flag remain required. No secret appears in the browser request or returned worker error. Redirects are rejected to avoid credential forwarding.

The worker's original runSeoSync orchestration is unchanged. Its transport now requires the prepared `operations/seo-vercel/supabase/migrations/20261018193508_seo_worker_run_control.sql`, generated by the CLI in the isolated worker package. Apply only after standalone decoupled 002, never unsafe 001; both operations require approval. The new migration adds only an SEO control table and four restricted RPCs. It enables RLS and denies direct application access. It revokes service-role access to the four old unfenced processing RPCs, so old standalone/Linux workers fail closed. Do not run old worker packages alongside this version or regrant those RPCs.

A single atomic database acquisition creates a 90-second run lease. Every processing step locks the control row, checks the run token and expiry, executes the existing queue function and persists counts within that SQL transaction. Overlapping manual/cron requests receive 409 without processing. Reconciliation locks, per-job SKIP LOCKED, job leases and atomic completion continue to protect queue work. A run exceeding its lease cannot issue further steps or finalize a replacement run. A database step already in flight holds the row lock until transaction completion, preventing takeover from interleaving with it. A crashed run becomes visibly interrupted after expiry; a later authorized invocation can recover it. Shared database resource exhaustion remains a risk; no commerce triggers or writes were added.

The worker still has a 45-second work deadline, 10-second request limits, 100-job cap and 30-second reserve before a new claim. Finalization has a separate bounded three-second request, with one additional bounded failure-finalization attempt if needed. These fit the configured 60-second Vercel maximum. The admin proxy waits at most 52 seconds and the browser 56 seconds. Client abort is not proof of SQL cancellation; actual hosted statement limits remain an acceptance gate. No background fire-and-forget continuation or self-invocation is used.

GET `/api/admin/seo/sync` reads only `seo_run_status()`. The UI polls every five seconds while mounted and shows running/completed/partial/failed/interrupted, persisted start/end time, completed/superseded/failed counts and sanitized error codes. It disables repeat clicks and refreshes catalogue data after success. Unknown HTTP outcome prompts inspection of persisted status instead of automatic retry. Counts are last-run counts, not a complete historical run audit. A lease token is never returned by the status RPC. Failed-job eligibility/backoff remains in the existing queue.

Scheduling stays disabled (`crons: []`). The Hobby daily proposal is unchanged. Manual operation is an explicit human action, not a timer or mechanism for bypassing Hobby cron limits. The previous dashboard catalogue-freshness warning is still 15 minutes and can appear between daily runs; persisted run status is a separate operational indicator. Daily updates/backlog recovery can exceed 24 hours.

## Rollout gates

1. Reverify the official project, fresh <=15-minute backup and exact reviewed SQL hashes; obtain separately scoped database approval. Preserve all prior backups.
2. Install standalone 002 and run its existing postflight before the run-control addition. Install the new run-control migration in its own approved transaction, then run `operations/seo-vercel/supabase/run-control-postflight.sql`. The old postflight's direct-worker EXECUTE assertion is intentionally superseded by the new fenced-access checks after the addition. No blanket migration push.
3. Independently verify actual PostgREST access: service role can discover the new RPCs; browser roles and old worker RPC calls are denied. No mutation probes under read-only authorization.
4. Separately deploy the worker disabled and verify the new dedicated project, Node 24, runtime, secrets and logs. Deploy the reviewed website candidate with manual activation off. No placeholder prebuilt upload.
5. Separately approve manual activation and one bounded run. Verify real admin permissions, duplicate manual/cron rejection, stored counts/persistence and catalogue coverage. No live product editing, order creation or fault injection is implied.
6. Daily cron activation remains a further approval. Verify delivery, alert routing and daily freshness acceptance. Pause the worker separately from any website rollback; retain all SEO data. Reverting worker code alone to its old version will fail because unfenced grants are revoked. Database repair/regrant/rollback requires a separate reviewed action.
